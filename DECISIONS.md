# DECISIONS.md

1. **Indexes.** I created a unique index on `employees(emp_code)` and `attendance(emp_code, date)` strictly to enforce deterministic deduplication dynamically avoiding explicit python locks. I created `attendance(date, late_minutes)` explicitly for the leaderboard (IXSCAN bounds logic natively bypassing scan load). I rejected compound `(date, status)` indices for `attendance_logs` because query sparsity wouldn’t justify the additional heavy index memory overhead given existing prefix filters.
2. **Punch-in race.** Assuming two identical `emp_code`/`date` punch-ins hit simultaneously, both attempt to `insert_one(doc)` into the unique `(emp_code, date)` compound index synchronously. MongoDB's native lock resolves the conflict; one operation succeeds successfully earning a `201`, whilst the trailing insert strictly faults with a `pyMongo.errors.DuplicateKeyError`. This is gracefully caught returning a `409 Conflict`.
3. **Ties.** Following standard dense-competition tie-breaks, if two employees tie precisely at rank 10 simultaneously mapping to the `limit`, *both* employees are distinctly returned natively yielding 11 rows. My `$setWindowFields` explicitly uses `total_late_minutes: DESC` in the partition, resolving `$rank` mappings equivalently to identical values before filtering by `>= limit`. Rows are secondary-sorted structurally by `emp_code ASC`.
4. **Headcount.** My Department Summary uses `employees` as its primary aggregating collection. It filters employees exclusively by testing `joined_on <= month_end`, subsequently performing `$lookup` cross-linking against `attendance_logs`. Therefore, users completely devoid of log records are retained accurately incrementing the raw `headcount`, rather than being invisibly trimmed by mapping logs first.
5. **One thing you would change.** Operating 100x datasets continuously executing pipeline window aggregations dynamically over sparse bounds natively stresses CPU overhead aggressively. I'd seamlessly migrate `$densify` analytics (monthly leaders, trends) into a materialized view asynchronously rolled up by scheduled batch jobs / triggers to heavily offload live queries.
